# plans/v0.2.0.md — v0.2.0 范围、里程碑与进度

> **定位**:v0.2.0 **不是重写**。v0.1.0 已发布且功能完整,这一版只做两件事:
> ①修掉 v0.1.0 基准**自己测出来的两个性能弱点**;②补齐验收口径要求、而 v0.1.0 缺失的**仓库记录**。
> **进度纪律**:同 v0.1.0 —— 不排日期,按实质进度推进;出口条件全部满足且证据可查才算完成。
> **外部约束**:十月赛事**报名与验收同为 2026-10-31**。最后 3 天留给验收材料与缓冲,**不安排编码**。

---

## 一、为什么要做这些(全部有实测依据,不是想当然)

| 依据 | 内容 |
|---|---|
| **基准实测** | 点查比朴素扫描快 ~236×、选择性遍历快 ~58×;但**胖桶遍历慢 ~5×、宽区间慢 ~21×**。根因已定位:每条产出记录一次 `(RowId, V)` 拷贝 |
| **基准实测** | `remove` 比 `insert` 贵 **20–44×**,且随 n 增长。根因:`order` 原地压缩是 O(len) |
| **验收口径** | "开发过程需在公开仓库持续提交,并保留 commits、**Issues、PR** 与更新记录" —— 仓库当前 **Issues = 0、PR = 0** |
| **SPEC §2.5.1** | 类型约束取并集(`K : Hash + Eq + Compare`)是 v0.1.0 **明确记录在案的取舍**,擦除方案列为 v0.2 候选 |

## 一·补 版本号判定:为什么是 `0.2.0`

按官方语义化版本口径(见 [`../RELEASE_CHECKLIST.md`](../RELEASE_CHECKLIST.md) 的「版本策略」一节),
递增哪一位取决于**改动的性质**。逐条判定本计划的改动:

| 计划内的改动 | 性质 | 依据 |
|---|---|---|
| M8 新增 id-only 游走 API | 向后兼容**新增** | 新方法,不动既有签名 |
| M8 新增 `swap_remove` 风格删除变体 | 向后兼容**新增** | 新方法,现有保序删除语义不变 |
| M9 Issues/PR 与文档 | 无 API 影响 | — |
| M11 `insert_or_replace` | 向后兼容**新增** | 新方法 |
| M11 **约束擦除**(`insert` 从 `K : Hash + Eq + Compare` 放宽到 `K : Hash + Eq`) | 向后兼容(**放宽**约束) | 既有调用方全部继续编译 |
| M11 `index_stats` 加分位数 | 向后兼容**新增**字段 | 需确认不破坏既有构造 |
| M12 发布 | — | — |

**结论:全部为向后兼容改动 → 递增 MINOR → `0.2.0`。** 这是 `moon.mod` 要写的版本号。

> ⚠️ **中途若发现某项无法做成兼容的**,必须**当场重新判定**:
> 要么改成兼容做法,要么按 MAJOR 递增(即直接 `1.0.0`),并写进 CHANGELOG。
> **不允许"反正还是 0.x 就随便破坏"** —— 见 RELEASE_CHECKLIST 的落地纪律第 4 条。
> 交付审核时,审核会话要**逐条核对本表与实际 diff 是否一致**。

| # | 里程碑 | 内容 | 出口条件 |

| **M8** | **修掉基准暴露的两个弱点** | ① **id-only 游走 API**:只产出 `RowId` 的遍历,避免每条记录拷贝;② **`swap_remove` 风格删除**:可选的 O(1) 删除(牺牲插入序稳定性,与现有保序删除并存) | 基准里**胖桶遍历**与**宽区间**的不利行显著收窄或转正,且 README 的取舍表更新;两组新 API 有测试覆盖;`remove` 的 O(1) 变体实测比现路径快一个量级 |

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| id-only API 扩大公开面,与既有 `(RowId, V)` 形状并存造成 API 膨胀 | 作为**独立方法**命名(如 `iter_ids_by`),不改既有签名;在 SPEC 里写清两者取舍,并让 README 给出选择建议 |
| `swap_remove` 变体破坏"插入序"这一公开承诺 | **不强改现有语义**,而是**新增**显式命名的变体;在 SPEC 里对照说明(参考实现 indexmap 的 `swap_remove` / `shift_remove` 二分) |
| `moon prove` 生态不成熟,探针可能卡住 | **限时**:先做最小可用探针;打不通就如实记录为"不可行"并转 Issue,不硬耗 |
| 15 天内改动过多导致 v0.1.0 的 78 条测试被破坏 | 每步跑全套;**既有断言一条都不许削弱**(与 v0.1.0 同一条纪律) |
| 发布后才发现问题 | v0.2.0 发布前必须跑 RELEASE_CHECKLIST Tier 0–4;发布后到 mooncakes 核对 `build_status` |
