# plans/v0.3.0.md — 0.3.0:验收否决的正确性修复与索引删除接口

> **定位**:0.3.0 不是功能版,是**验收否决后的正确性修复版**。2026-11-08 的验收意见指出三件事:
> ① 申报的「按需增删索引」只交付了「增」,没有公开删除接口;② 通过 `get` 拿到记录后修改被索引字段,
> 会旧键命中 / 新键漏查 / 自检失败;③ 外部可变引用的限制没有写成契约,多索引一致性保证不完整。
> 三条**经审核会话逐条复现,全部成立**,并有两处比意见原文更严重(见 §二)。
> **纪律**:同 v0.2.2 —— 不排日期;出口条件全部满足且证据可查才算 ✅;执行会话只报「待审核」。
> **来源**:仓库外 `v0.2.2-草案.md` 附录 G(评审会话方案)+ 审核会话 2026-11-08 的独立复现与裁定。

## 二、复现证据(审核会话,2026-11-08,用已发布的 0.2.2)

探针:`struct Rec { tags : Array[Int32] }`,`register_unique("first", fn(r) { r.tags[0] })`。

| 场景 | 实测 | 结论 |
|---|---|---|
| `get` 后改 `tags[0]` | `k1=hit k2=miss verify=Err(I4 …)` | 验收意见原文那一幕 |
| `modify` 闭包里就地改 | `modify: Ok`,之后 `k1=hit k5=miss verify=Err` | **库自己的 API 就能写坏**,不是用户误用 |
| 脏索引下 `remove` | `RuntimeError: unreachable` @ `Index::remove` | 删不掉,只剩 `clear()` 丢全表 |
| 脏索引下 `update` | `RuntimeError: unreachable` @ `Index::retarget` | 改不了 |
| 脏索引下插同键 | `insert … Ok`,`len=2` | **唯一性被绕过** |

文档反话(必须改):`docs/SPEC.md:519`「不存在调用方拿到 `&mut` 后破坏不变量的路径」、`:457`「取 `V` 是一次拷贝」、
`README.md:211`「每次产出一条记录都会拷贝一次 `V`」、`src/table.mbt:138-139` 注释。

## 四、验收场景(0.3.0 的验收标准,缺一条都不算完)

| 场景 | 操作 | 预期 |
|---|---|---|
| 删除正常 | 注册两索引 → 删其一 | `true`;`has_index=false`;`len`/`iter` 不变;`verify=Ok` |
| 删除幂等 | 再删同名 | `false`;不 abort;状态不变 |
| 删除未知 | `unregister_index("ghost")` | `false`;不 abort |
| 重注册 | 删除后同名重注册 | 回填成功;旧键不命中;新键命中;`verify=Ok` |
| 约束释放 | 删唯一索引后插重复键 | 从 `Err` 变 `Ok` |
| 可变 V 检测 | `get` 后改被索引字段 | `verify` 报 I4(契约写明:不承诺修复外部别名) |
| `modify` 就地改 | `modify(id, fn(r){ r.k = 5; r })` | 旧键不命中、新键命中、`verify=Ok` |
| 脏索引删除 | 外部改坏后 `remove`(脏的是**被删的那条**) | 返回记录、不 panic、`verify=Ok` |
| 脏索引更新 | 外部改坏后 `update`(脏的是**被更新的那条**) | 成功;新键命中;旧桶清掉 |
| 兼容 | 原 148 条测试 | 全绿;mbti 只新增 `unregister_index` + VERSION |
| 残余边界(仅记录,不要求通过) | 脏的是**另一条**记录时 `remove`/`update` | 仍可能 `verify=Err`;脏表 `insert` 唯一性预检可能被绕过 —— 见 SPEC §3.7 与 README「脏表的残余边界」 |

## 五、审核会话的裁定(2026-11-08,执行按这里)

1. **`unregister_index` 返回 `Bool`**,未注册返回 `false`,`**不 abort**`;这是 §7.1「未知索引名 abort」的**显式例外**,写进 SPEC。
2. **不 bump `version`**:I8 定义 `version` 为记录变更计数,删索引不改记录。先用测试钉死「删除后旧的 `iter_by` 游标仍能走完」;
   若实测游标会炸,则改为 `+1` 并把 I8 改成「记录或注册表变更」—— **用证据定**。
3. **`remove` / `swap_remove` / `update` 都做成 total**,共用同一套「扫描找槽」慢路径,不许写两套逻辑;正常路径不得触发扫描。
4. **不加 `rebuild_index`**:恢复路径 = `unregister_index` + 重新 `register_*`(注册自带回填)。
5. **申报书必须改**:它是这次否决的直接证据,版本/测试数/「增删」表述都要对上。
6. 允许的行为变化只有三类:新增一个方法、把两处 panic 变成可用、修 `modify` 的静默损坏。**任何其他公开 API 变化一律先问。**
